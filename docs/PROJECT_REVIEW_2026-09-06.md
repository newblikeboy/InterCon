# InterCon project review — 6 September 2026

**Historical review snapshot:** the findings below describe the project before implementation. See [the fix report](FIXES_PLAIN_LANGUAGE_2026-09-06.md) for current status and remaining limitations.

For explanations without technical terms, read the [plain-language findings](PROJECT_REVIEW_PLAIN_LANGUAGE_2026-09-06.md). Finding numbers match this report.

**Verdict: not ready for a broad commercial launch.** The customer interface has a consistent visual foundation and responsive layouts. Release blockers remain in tenant isolation, login protection, consent enforcement, billing, inbox correctness, and database initialization. Some advertised capabilities are still scaffolding.

This is a review of the supplied checkout, not certification of a deployed service. Application code and dependencies were not changed.

**Scope and evidence**

- Reviewed the project structure, application startup, middleware, routes/controllers, models/index setup, authentication, billing, contacts/groups, Meta onboarding, templates/media, message and webhook workers, realtime delivery, public API, landing page, customer portal, admin portal, and operational documentation.
- `npm run check`: passed for 95 JavaScript files.
- `npm test`: 9 tests passed. They cover middleware, token signing/encryption, public prices, headers, origin enforcement, signup validation, and webhook signature rejection. They do not establish billing, queue, database, or UI correctness.
- `npm audit --omit=dev --json`: 5 vulnerable production dependency entries: 2 high, 2 moderate, 1 low.
- Eight isolated backend reproductions used the actual application functions with fake model/provider responses. No live database or provider mutations were performed. Results: [backend reproductions](review-2026-09-06/reproductions.json).
- Chrome/Playwright inspected landing/login and 12 customer views at 1440, 390, and 320 CSS pixels. No page-level horizontal overflow or uncaught JavaScript exceptions occurred in that sample. Customer API data was mocked, mostly as empty states; Facebook/other external browser requests were blocked. A reconnecting indicator in these screenshots is expected from this isolated setup.
- Additional browser checks reproduced broken CSV parsing, admin visibility, and fragment routing: [UI reproductions](review-2026-09-06/ui-reproductions.json). [Browser observations](review-2026-09-06/browser-results.json).
- Live MongoDB indexes, Redis failover, payment capture/refunds, email delivery, Meta approval/onboarding, WhatsApp sends, restore procedures, production performance, real customer data, and cross-browser accessibility remain unverified.

**High-priority bugs and release blockers**

1. **Phone-name webhooks can lose their tenant restriction.** `src/services/webhook.service.js:486` builds a Tenant query using `{ tenantId }`, although Tenant identifies itself with `_id`. Database startup enables `strictQuery`, which removes the unknown field. Reproducing query casting with a name-update payload without `display_phone_number` produced an empty filter `{}`. The resulting update can affect an unrelated tenant. When a phone filter is present, the query still lacks explicit tenant isolation. Fix the predicate to `_id: tenantId` and test tenant A/B isolation through the real webhook processing path.

2. **Login/signup throttles accept attacker-controlled identities.** `src/middleware/security.js:24` gives any `X-API-Key` header precedence, including on unauthenticated login routes. Arbitrary cookie values also create distinct buckets. In a local test with the login limit set to 3, ordinary requests became HTTP 429 after the third request; all six requests with changing bogus API-key headers reached the controller. Use independent IP and normalized-account throttles for authentication, and only use verified identities for authenticated quotas. Redis storage alone does not fix the key selection.

3. **Sending by phone number reactivates blocked or opted-out contacts.** `src/services/message.service.js:584` upserts `status: "active"` and `optIn.status: true` when a phone-based API send includes an opt-in flag. The eligibility check runs after this overwrite. The isolated reproduction changed a blocked contact into an active, opted-in contact. Preserve existing suppression state and require a distinct, auditable re-consent/unblock action.

4. **Queued sends do not recheck current contact or workspace eligibility.** `src/services/message.service.js:986` checks tenant existence, credentials, template approval and sending limits, but does not reload contact suppression state, check tenant suspension, or recheck paid-plan expiry. Queue a message, then block the contact or suspend the workspace while it waits: the worker still has a path to send. Revalidate eligibility immediately before provider delivery and record a clear cancellation/failure reason.

5. **Opening a new checkout removes existing paid access.** `src/services/billing.service.js:119` replaces the active subscription fields with the new selection and sets `pending_payment` before payment succeeds. The reproduction changed paid access from true to false merely by calling `selectPlan`. Cancelling checkout does not restore the old subscription. Keep pending orders separate from the active entitlement, and change the entitlement only after verified capture.

6. **A successful payment can be stranded when the browser callback is lost or a newer order is created.** `src/services/billing.service.js:231` verifies only the tenant's current `razorpayOrderId`. `selectPlan` overwrites that field, while Payment records are created only after browser verification. The repository has no Razorpay webhook or reconciliation worker; webhook routes are for Meta. Completing an older checkout after opening a second one is rejected. Closing the browser before verification also leaves no automatic activation path. Persist each order and reconcile captured payments independently of the open browser, with idempotent activation.

7. **Template synchronization can disable valid templates beyond page one.** `src/services/template.service.js:415` fetches `limit=100`, ignores `paging.next`, then disables locally stored approved/review/paused templates absent from that one response once the five-minute grace period passes. A fake response containing a next page resulted in exactly one provider request followed by the disabling update. Fetch the complete authoritative collection before deciding a template disappeared; an incomplete sync must never disable unseen records.

8. **Long inbox conversations hide the newest messages and mark them read.** `src/services/inbox.service.js:133` sorts ascending and takes the first 200 messages, without pagination. It then clears the conversation unread count. A 205-message fixture returned messages 1–200 and cleared all five unread messages. Fetch the newest page, display it chronologically, expose older-page cursors, and only acknowledge the messages actually read. Conversation listing also caps results without a way to page through older chats.

9. **Required uniqueness/index guarantees are not provisioned completely.** `src/config/database.js:14` disables automatic indexes. `src/config/indexes.js:60` provisions only a subset of schema indexes. Missing provisioning includes unique user email, tenant/contact phone, tenant/conversation phone, inbox provider-message ID, template name/language, and outbound idempotency key. The outbound queue claim index is also omitted. On a fresh database without separately applied migrations, duplicate prevention and query performance differ from the model declarations. Add an explicit, repeatable index migration and validate it against a clean replica-set database. Existing production indexes were not inspected.

10. **Meta onboarding saves supplied asset IDs even after subscription failure.** `src/services/meta.service.js:940` skips token asset discovery when both IDs are supplied. It checks whether another InterCon tenant has claimed the IDs, but does not prove that the exchanged token owns the supplied WABA or that the phone belongs to it. Subscription failure is caught and the supplied IDs are still persisted, with `meta_connected` based on the presence of a phone ID. This can falsely claim unowned/unconnected assets and presents an ownership risk for IDs not yet claimed in InterCon. Validate provider ownership and the WABA/phone relationship before binding them; keep connection failures separate from successful connection state. This is a source-confirmed missing validation, not a live Meta exploit demonstration.

11. **A local write failure after provider acceptance can trigger duplicate delivery.** `src/services/message.service.js:906` (`acceptMessage`) writes the accepted message state and then RecipientUsage. A failure in either write propagates to the outer catch in `processNextQueuedMessage`, which can reschedule the provider send. If Meta accepted the request, retrying delivery is unsafe; even a successful accepted-state write can be overwritten by a retry schedule when the later usage write fails. Separate provider delivery from local bookkeeping retries and preserve an accepted/uncertain terminal delivery outcome.

12. **Vulnerable spreadsheet parsing is exposed through the UI.** `package.json` and the bundled `Public/vendor/xlsx.full.min.js` use SheetJS 0.18.5; `Public/js/customer-portal.js:1454` reads user-selected spreadsheets in the browser. The audit reports SheetJS prototype pollution and ReDoS. Fix both the dependency and the vendored browser asset; `npm audit fix` alone has no advertised fix for the npm `xlsx` package. The advisory describes [prototype pollution when reading crafted files](https://github.com/advisories/GHSA-4r6h-8v6p-xvw6) and [ReDoS before 0.20.2](https://github.com/advisories/GHSA-5pgg-2g8v-p4x9). Other audit entries are `ip-address` (high), `mongoose` and `qs` (moderate), and `body-parser` (low). These are dependency findings; exploitability of every advisory in this application was not established.

**Other confirmed defects and material gaps**

13. **Early plan replacement discards remaining prepaid time.** `src/services/billing.service.js:343` calculates the new period from the capture time, irrespective of the previous paid-through date. The same formula exists in administrative activation. The isolated administrative-activation reproduction replaced approximately 90 remaining days with one month. Define plan-change/renewal semantics, preserve or explicitly credit unused entitlement, and clamp month-end arithmetic rather than relying blindly on `Date.setMonth` rollover.

14. **Worker-originated realtime notifications cannot reach browser sockets.** `src/services/realtime.service.js:6` stores clients only in an in-process Map. `src/workers/webhookQueue.worker.js` runs separately from the HTTP/WebSocket server, so `publishInboxUpdated` sees no connected clients there. Separate API instances have the same problem. Polling provides eventual updates, but the UI's live connection does not mean webhook events are delivered immediately. Add inter-process fan-out, such as Redis pub/sub, and test with two API processes and a separate webhook worker.

15. **Out-of-order webhooks regress delivery state.** `src/services/webhook.service.js:165` unconditionally overwrites status and ignores provider timestamps/state progression. Replaying a late `sent` event changed a `read` fixture to `sent`. Store provider timestamps and enforce valid state transitions. Inbound processing similarly overwrites conversation timestamps from each arriving event; delayed events can move the conversation preview and service-window timestamp backward.

16. **CSV imports corrupt valid quoted fields.** `Public/js/customer-portal.js:1435` splits each line on commas, without CSV quoting rules. Browser reproduction: `"Doe, Jane",919876543210,Delhi` became name `"Doe`, phone `Jane"`, city `919876543210`. Quoted commas/newlines can therefore reject contacts or misassign fields. Use one correct CSV parser for both contact and variable imports. Also surface the server's row errors: the contact-import UI currently displays imported/skipped counts but discards the explanatory `result.errors` array.

17. **The contact picker silently stops at 100 contacts.** `src/services/contact.service.js:51` limits the list to 100 without pagination metadata. `Public/js/customer-portal.js:1680` requests `/api/contacts` without pagination, and the recipient search filters the loaded subset. Importing more than 100 contacts succeeds, but older contacts are inaccessible through that picker and “Select all contacts” covers only loaded contacts. Group-based sending can include additional contacts, so this is not a global 100-recipient sending limit. Implement server-side search and explicit pagination/all-matching selection. Media listing similarly returns 200 while the configured asset quota allows 500; group members stop at 500.

18. **Bulk submissions have no request-level idempotency.** `src/services/message.service.js:735` generates a new random batch ID on every submission and inserts a new batch. The customer form sends no idempotency key. If insertion succeeds but the response is lost, retrying the action can queue the audience twice. Persist an idempotency key per confirmed send, and return the existing batch for retries of the same request.

19. **Campaigns and automations are storage/status scaffolding.** `src/services/campaign.service.js` creates documents and updates a status string; no worker scans scheduled campaigns or queues their recipients. `src/services/automation.service.js` stores flows, but webhook processing never looks up or executes active flows. These endpoints must not be treated as finished scheduling or auto-reply functionality. The current customer portal's direct bulk sender is a separate implemented path; it does not complete the campaign scheduler. Remove unfinished claims from the paid offering or implement and test the promised behavior.

20. **The admin console is a public prototype, and its navigation does not hide the launcher.** `Public/js/admin-portal.js:260` renders descriptive task lists and related links; it never loads admin operational data or checks authentication. `/admin` serves the static shell. No confidential admin data exposure was demonstrated because the displayed content is static. Browser inspection of `/admin#customers` also found `home.hidden === true` while computed `display` remained `grid`, leaving the launcher above the detail screen. Respect `[hidden]` in the admin stylesheet. Implement authenticated, role-checked operational screens before using this as an administration product.

21. **Modal and account UX is incomplete.** `Public/js/landing.js:34` moves initial focus into the dialog but does not trap focus or restore it on close. Tab escaped behind the visible login modal at all three tested widths. [W3C's modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) specifies contained keyboard navigation and appropriate focus restoration. The login “Remember me” checkbox (`Public/index.html:495`) has no name/handler and does not affect the fixed cookie lifetime. No password-reset flow exists in `src/routes/auth.routes.js`. “Need help?” links to the underlying contact section without closing the overlay. Build a usable recovery flow and make every displayed authentication control work.

22. **An existing DOM ID can blank the customer view.** `Public/js/customer-portal.js:252` considers any `document.getElementById` match a valid portal view. Visiting `/customer#template-modal-title` reproduced zero visible portal views, because that ID belongs to a heading rather than a view. Restrict accepted fragments to registered `[data-portal-view]` elements. Navigation also uses `replaceState` for normal transitions, so browser Back does not retrace ordinary portal navigation.

23. **Logout failure is presented as a successful departure.** `Public/js/customer-portal.js:3985` redirects in `finally` and ignores the logout response status. A rejected logout can leave the cookie/session active; the landing page then detects the active session and redirects back into the portal. Handle non-success responses explicitly and provide a retry state rather than implying the session ended.

24. **Metrics allow unbounded path cardinality.** `src/services/metrics.service.js` stores request-path-derived keys in Maps without a cap or expiry. It runs before routing/security in `src/app.js`, including for arbitrary unknown paths. Distinct nonnumeric URL segments create permanently retained counters/timings, and the metrics snapshot grows with them. Record matched route templates and one bounded not-found label; cap retained labels.

**Recommended release sequence**

1. Fix tenant isolation, ownership verification, authentication throttles, suppression enforcement and required indexes. Verify them with tenant A/B and concurrent-request tests against a clean replica-set database.
2. Fix billing/order persistence and reconciliation, queue delivery bookkeeping/idempotency, full template synchronization and inbox pagination. Test provider success followed by local write failure, abandoned checkout, duplicate callbacks, delayed/out-of-order webhooks, and large contact/template/chat collections.
3. Finish or remove unfinished paid-feature claims, implement actual admin operations, restore reliable cross-process realtime, and complete account recovery and keyboard behavior.
4. Validate the finished flows in a provider sandbox/staging environment with Redis and separate workers; check fresh deployment, migration, backup restoration, meaningful load targets, and populated desktop/mobile states.

The project has enough implemented structure to continue developing toward release. Passing the current nine tests and having polished screens is insufficient evidence for accepting paying customers without resolving these blockers.
